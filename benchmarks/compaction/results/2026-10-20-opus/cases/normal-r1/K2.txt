1. Primary Request and Intent:
   The goal is resumable parallel uploads for the Driftship CLI, a TypeScript tool at /work/driftship on branch feature/resumable-upload. The existing command is `driftship push <directory> --to <url>`. Requirements:
   - Zero runtime dependencies and Node 22 or later. This round covers local development and tests only.
   - Do not publish, merge, or push anything to a remote.
   - Use 4 workers and 4 MiB chunks to match the server. "Four retries" means four extra attempts after the first, so five attempts in total.
   - The journal lives at `.driftship/resume-v1.json` inside the source directory. Resume is on by default. It must be durable on removable drives: write a temp file, fsync it, rename it, then fsync the directory.
   - Resume is controlled by `--resume=on|off`, default on. `verify` is rejected for now. There is no `--no-resume` alias. `off` starts fresh locally and never deletes or aborts remote sessions.
   - Reject destination URLs that contain a query, a fragment, or userinfo. The only allowed normalization is adding a trailing slash. Authentication comes only from the DRIFTSHIP_TOKEN environment variable. Errors must never echo the URL or the token.
   - Resume identity is the full SHA-256, the size, and the nanosecond mtime. Write serialization must not use a database or add a dependency.
   - Handle lost responses. A part can be stored before the socket dies, and a completion can succeed before its response is lost. Neither case may produce a duplicate object or a skipped part.
   - Dry-run makes zero network calls and creates no .driftship directory. Scanning to compute plan totals is fine.
   - Only idempotent PUT parts may retry. Begin and complete are never retried automatically. After an ambiguous complete failure, one status GET is allowed. If that GET fails, return its error and let the next run resume.
   - Cancellation exits with 130. It settles journal writes that are already queued and schedules no new upload work.
   - Remote cleanup is out of scope.
   - JSON mode adds one UUID `run_id` per invocation to every event. The field `type` stays as the discriminator. The completion event carries files, bytes, uploaded_bytes, and resumed_bytes. uploaded_bytes counts confirmed unique bytes, not retransmitted traffic.
   - Snapshots, file locks, copy-on-write, and watchers are out of scope. Users must not modify the directory during an upload, and a detected change is a failure.
   - Before accepting resumed parts, check status.file_size, status.file_sha256, and status.part_size. A mismatch is `session_mismatch`, with no silent replacement. Only missing (404) or expired sessions restart automatically.
   - Exit codes: 0 success; 1 transport, server, or ordinary local I/O failure; 2 usage or configuration; 3 invalid or mismatched local resume state; 130 interruption. A server checksum mismatch is 1. session_mismatch is 3. Ordinary permission errors are not 3.
   - The concurrency option accepts 1–16. Effective concurrency is min(user setting, server maximum_parallel_parts). Malformed discovery data, or any protocol other than 3, fails before begin, with no guessed defaults. Dry-run may show the requested concurrency.
   - Do not claim production readiness, because no real storage service has been tested.

2. Key Technical Concepts:
   - Object store protocol revision 3, from docs/server-protocol.md:
     - Capabilities: min 1 MiB chunk, max 16 MiB, preferred 4 MiB, max 4 parallel parts, sha256 checksums.
     - Sessions: POST uploads opens one. PUT parts are one-based, with Content-Length and X-Part-SHA256, and exact replay returns 204. 422 means checksum_mismatch and 409 means part_conflict.
     - GET status returns open, complete, or expired; parts may arrive unordered; a missing session is 404. POST complete receives the sorted parts plus the whole-file sha256.
     - Retryable statuses are 408, 429, 500, 502, 503, 504. 401 and 403 are permanent. Redirects are not supported.
     - Empty files use begin and complete with zero parts.
   - One global bounded worker pool fed by a lazy part iterator.
   - Journal writes serialized through a promise queue (JournalStore). Once a write fails, the store stays failed.
   - Durable atomic write: temp file with mode 0600, fsync, rename, fsync the parent directory (mode 0700).
   - Retry-After parsing (delta seconds or HTTP date) with exponential backoff and jitter, capped at 30 s.
   - Receipt validation checks path, bytes, sha256, and etag.
   - TransferMetrics deduplicates confirmations by the key JSON.stringify([path, part]). A receipt uses part key 0.
   - The local fake HTTP server harness keeps remote state separate from response delivery so faults can be injected.

     ```ts
     export function retryDelay(header:string|null,now:number):number|undefined {
       if(!header)return undefined;
       const seconds=Number(header);
       if(Number.isFinite(seconds)&&seconds>=0)return seconds*1000;
       const date=Date.parse(header);
       if(!Number.isNaN(date))return Math.max(0,date-now);
       return undefined;
     }
     ```
     The retry loop computes `delay=after??Math.floor(min(30000,500*2**attempt)*(0.5+random()*0.5))`.
